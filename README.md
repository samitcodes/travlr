# Architecture

In my full stack project, I used a few different frontend approaches, each with its own role. The Express HTML frontend used server-side rendering, where pages were generated on the backend and sent directly to the browser. This was straightforward and worked well for basic pages, but it required full page reloads whenever data changed. JavaScript was then used on the client side to add interactivity, such as handling form inputs and making API requests, which helped improve the user experience without constantly reloading pages. The single-page application (SPA), built with Angular, handled most of the dynamic functionality. It managed routing and UI updates in the browser and communicated with the backend through APIs, which made the application feel faster and more responsive. The backend used a NoSQL MongoDB database because it fits naturally with the MEAN stack and works well with JavaScript-based applications. MongoDB stores data in a JSON-like format, making it easy to send and receive data between the backend and the Angular frontend. Its flexible schema made it easier to update and change data models as the project evolved, without needing complex migrations. MongoDB also scales well and supports rapid development, which made it a practical choice for a full stack application that could grow over time.

# Functionality

JSON is different from JavaScript because it’s not a programming language; it’s just a data format used to store and transfer information. JavaScript is responsible for the logic of the application, like handling user interactions, making API calls, and controlling how data is displayed. Even though JSON looks similar to JavaScript objects, it doesn’t support functions or logic. In the full stack project, JSON tied the frontend and backend together by serving as the standard format for API communication. The backend sent data from MongoDB to the frontend as JSON, and the frontend used that data to render views and send updates back to the server in the same format. During the full stack development process, I refactored code several times to improve functionality and efficiency. On the backend, I reorganized routes and separated controller logic to make the code easier to maintain and debug. On the frontend, repeated UI elements like forms and data displays were refactored into reusable components instead of being duplicated across pages. This reduced redundancy and made updates faster and less error-prone. Reusable UI components also improve consistency across the application, speed up development, and make it easier to scale and add new features.


# Testing

In a full stack application, methods, endpoints, and security all work together to control how data is requested, modified, and protected between the frontend and backend. API methods (such as GET, POST, PUT, and DELETE) define what action is being performed. For example, GET is used to retrieve data, POST is used to create new records, PUT or PATCH updates existing data, and DELETE removes data. Each method targets a specific endpoint, which is the URL path that represents a resource in the system, like "/api/trips" or "/api/users/:id". When testing APIs, it’s important to verify that each endpoint responds correctly to the appropriate method, returns the expected status codes, and handles invalid input properly. Security adds another layer of complexity to both development and testing. In a full stack application, endpoints are often protected using authentication and authorization mechanisms such as tokens or middleware. This means testers must include valid credentials or tokens in their requests to access secured routes. Testing must also confirm that unauthorized users are blocked, sensitive data is not exposed, and error responses do not reveal internal system details. Overall, understanding how methods map to endpoints—and how security controls access to them is critical for building a reliable and secure full stack application.
